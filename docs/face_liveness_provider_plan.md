# 人脸识别与活体能力选型

## 当前结论

虹软 ArcFace Android V3.0 在当前 Android 15 真机上激活返回 `90122`，结合控制台说明其主要支持 Android 10，不能作为本项目的广泛适配主链路。

项目当前采用：

- App 端：Google ML Kit 人脸检测做正脸、左转、右转等动作采集校验。
- 后端：腾讯云人脸库注册、搜索和比对；百度人脸服务保留为历史/备用实现，不作为当前推荐主链路。

该方案不是金融级动作活体核身，但不依赖企业核身 SDK 授权，Android 兼容性更好，适合当前个人权限阶段继续打磨真实业务流程。

## 推荐服务

1. 腾讯云人脸核身
   - 优点：核身链路成熟，适合动作活体、实名核验类场景。
   - 限制：通常需要企业资质、服务开通、计费和 SDK 授权。
   - 适合：学校正式上线前的合规核身能力。

2. 阿里云金融级实人认证
   - 优点：金融级实人认证链路完整。
   - 限制：接入门槛、业务审核和成本较高。
   - 适合：高合规要求的身份核验。

3. 百度智能云人脸实名认证/核身 SDK
   - 优点：可与现有百度人脸库、百度云配置衔接。
   - 限制：动作式动态活体能力通常需要企业或核身服务权限。
   - 适合：继续沿用当前百度后端能力时升级。

4. 旷视 FaceID
   - 优点：活体与核身能力成熟。
   - 限制：SDK 与服务开通需要商务/资质流程。
   - 适合：对动作活体体验要求较高的正式项目。

5. Google ML Kit Face Detection
   - 优点：端侧检测、安装门槛低、兼容面较广，适合实时姿态/质量校验。
   - 限制：不是反欺诈级活体核身，不能单独抵御屏幕翻拍、视频重放等攻击。
   - 适合：当前个人权限下实现“比静态照片更严格”的动作采集。

## 后续接入路径

拿到正式核身 SDK 或云服务密钥后，应新增独立 `FaceProvider` 实现，而不是改动打卡业务逻辑：

- 注册：App 调用 SDK 完成动作活体，后端保存核验流水号和人脸库标识。
- 打卡：App 调用 SDK 完成实时活体，再将核验 token/图片摘要提交后端。
- 后端：校验供应商返回结果、用户身份、分数阈值、核验时间窗口。
- 数据库：记录 `provider`、`livenessMode`、`verifyRequestId`、`score`、`riskLevel`。

当前版本以端侧 ML Kit 动作采集补强用户体验和基础防代签能力，以腾讯云人脸库承担服务端注册与比对。
